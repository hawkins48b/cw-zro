# Dope card names outside WinAnsi, and a length limit for profile names

- **Date:** 2026-11-11
- **Branch:** task/140-141-text-limits
- **Issues:** [#140](https://github.com/hawkins48b/cw-zro/issues/140), [#141](https://github.com/hawkins48b/cw-zro/issues/141)
- **Status:** Not in production yet

## Summary

Two issues found in the security review of #136-#139, in one branch. Both behaviours were already in production.

| Issue | Change |
|-------|--------|
| #140 | A rifle name, ammo brand or optic name with emoji, CJK, Cyrillic, `ł` or another character outside WinAnsi no longer fails the dope card. Those characters are left out of the card header. A space character the font cannot encode, such as U+202F, prints as a space |
| #141 | The rifle designation, optic name and ammo brand inputs take at most 60 characters. A longer stored value is cut to 60 when it is read, and the stored ammo text (`ammo`) to 80. Duplicating a profile keeps the " - Copy" suffix within the 60 characters |

**Release notes:**

- Dope cards print for names with emoji or non-Latin letters. Those characters are left out of the card.
- Rifle, optic and ammo brand names are limited to 60 characters. Longer saved names are shortened.

## Owner decisions (2026-11-11)

| Question | Decision |
|----------|----------|
| #140: replace with `?`, drop, or embed a Unicode font | Drop each character the font cannot encode. No font is embedded and no dependency is added |
| #141: the limit | 60 characters |
| #141: a longer stored value | Cut it when read |

## Implementation

| Part | What it does |
|------|--------------|
| `encodableText(font, text)` in [`dopeCardLayout.js`](../src/lib/utils/dopeCardLayout.js) | Keeps the characters in the font's `getCharacterSet()` (218 code points for Helvetica Bold), read once per font. Other characters are dropped, and lone surrogates too. A Unicode space separator (`\p{Zs}`) it cannot encode becomes a space. This choice is mine; the owner decided "drop", and without it `55 gr` would print as `55gr`. `drawHeaderText` calls it after the control characters become spaces (#137) and before `fitText`, so every header field of both cards goes through it |
| `MAX_NAME_LENGTH` (60), `MAX_AMMO_LENGTH` (80), `cutText` in [`storedProfiles.js`](../src/lib/utils/storedProfiles.js) | `normalizeProfiles` cuts a text `name`, `opticName`, `optic` or `bulletBrand` longer than 60 UTF-16 code units, and a text `ammo` longer than 80, on a copy of the profile. `ammo` gets 80 because the form builds it from the brand and the weight (`buildAmmoString`). `cutText` counts UTF-16 code units, as `maxlength` does, and does not leave the first half of an emoji at the end. Values that are not text are left for `shownProfile`, as before. The id renumbering of #131 and #134 is unchanged |
| [`ProfileForm.svelte`](../src/lib/components/ProfileForm.svelte) | `maxlength={MAX_NAME_LENGTH}` on the three inputs |
| `copyName` in [`profileOps.js`](../src/lib/utils/profileOps.js) | The copy's name, cut to 53 characters before " - Copy" is added. Used by `duplicateProfile` and the profiles page (review finding) |

A cut stored value is written the next time the user saves the profile list. The load migration in `profiles.svelte.js` does not write for a cut alone.

## Security review

Round 1: **PASS**. The reviewer passed every code point from U+0000 to U+10FFFF, and lone surrogates, through the header path with the real pdf-lib font, and none threw. `encodableText` is linear: 5 million characters took about 0.8 s. Cutting on read does not change ids or the order of the list. Three Low findings:

| Finding | Outcome |
|---------|---------|
| A copy of a 60-character name lost its " - Copy" on the next read | Fixed with `copyName` |
| `ammo` can be written longer than 80 when the weight is a long decimal | Left: it is cut on read |
| A cut by code units can split a joined emoji or a letter from its accent | Left: it matches `maxlength`, and only the last character looks damaged |

Round 2, on `copyName`: **PASS**. Both duplicate paths use it, a damaged name still gives text, and it adds no new import cycle.

Pre-existing, reported and not fixed: the `bc` and `bcType` header text is printed from storage without a length limit (a multi-megabyte `bcType` costs under a second per card, and no longer fails it). Reading `profiles.list` makes a new object on every read for each cut or renumbered profile, as renumbered ids already did.

## Limitations

- A name made only of characters the font cannot encode prints as an empty field.
- The card does not tell the user that characters were left out.
- Not checked in a browser: `maxlength` is standard HTML, and only the source is tested.
- Turning U+202F and other spaces into a plain space is my choice, not the owner's.
