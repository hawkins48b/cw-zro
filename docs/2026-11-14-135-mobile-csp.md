# Content-Security-Policy in the mobile build

- **Date:** 2026-11-14
- **Branch:** task/135-mobile-csp
- **Issue:** [#135](https://github.com/hawkins48b/cw-zro/issues/135)
- **Status:** Delivered, still to check on a device (the issue stays open for it)

## Summary

Since #104, the web and desktop builds carry a Content-Security-Policy. The mobile build (`npm run build:mobile`, Capacitor) had none, because nobody here can run it on an Android or iOS device.

**Delivered:** the mobile build writes the same policy as a `<meta>` tag. It also lists `capacitor://localhost` in each source list that has `'self'`. The web and desktop policy did not change. No calculated result changed. Whether the Android and iOS web views run with no CSP violation must still be checked on a device or emulator.

## Technical changes

- [`vite.config.js`](../vite.config.js): `csp` is passed to SvelteKit for every build, not only for web and Electron. The mobile build keeps `bundleStrategy: 'single'`. `appOrigins` is `['self']`, or `['self', 'capacitor://localhost']` for `BUILD_TARGET=capacitor`. It is used in `default-src`, `script-src`, `style-src`, `img-src`, `font-src` and `connect-src`.
- [`docs/architecture.md`](architecture.md#content-security-policy), [`docs/data-and-privacy.md`](data-and-privacy.md) and [`docs/deployment.md`](deployment.md): describe the mobile policy and why it needs no more sources.

### Why these sources

| Web view | App origin | Covered by |
|----------|------------|------------|
| Android | `https://localhost` | `'self'` |
| iOS | `capacitor://localhost` | `capacitor://localhost`, listed because `'self'` may not match a custom scheme |

- Both origins also serve Capacitor's `/_capacitor_file_` and `/_capacitor_http_interceptor_` paths, so they need no other source. The app uses neither.
- Native bridge: Android adds it with `addDocumentStartJavaScript` where the WebView supports it, which the page policy does not cover. On older WebViews `JSInjector` inserts it as an inline `<script>` right after `<head>`. That is before the policy `<meta>`, and a `<meta>` policy does not apply to anything before it. iOS adds the bridge as a `WKUserScript`, which the page policy does not cover either. `native-bridge.js` uses no `eval`.
- The native side calls the page through `evaluateJavascript`, which the page policy does not block.

### Checks

## What the owner should test

On an Android and an iOS device or emulator (`npm run build:mobile`, `npx cap sync`, then run from Android Studio and Xcode), open the web view console (Chrome `chrome://inspect`, Safari Web Inspector) and check:

1. The app starts. The console shows no `Content-Security-Policy` or `Refused to` message.
2. A calculator gives a result (WebAssembly engine, `'wasm-unsafe-eval'`).
3. The trajectory charts draw.
4. A dope card PDF is created and can be saved or shared. On Android this may fail for a reason that has nothing to do with the policy (see Security review).
5. The splash screen hides, and the status bar works.

If a violation shows, its message names the directive and the blocked source. Add that source in `vite.config.js` for the mobile build only.

## Security review

**PASS.** One Low finding was fixed: the comment and docs now name Android's document-start script as the main path for the bridge.

**Pre-existing, for the device test:** an Android WebView usually ignores a click on a `blob:` `<a download>` link unless the app sets a `DownloadListener`. The page also revokes the URL right after the click. Either can stop the dope card PDF from saving on mobile. Neither is caused by the policy.
