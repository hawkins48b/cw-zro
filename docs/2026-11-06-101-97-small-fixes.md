## Decisions

**Two wind getters (#118).** On #116 the owner decided that a stored array, object or boolean speed or direction gives no result. Falling back to the default wind would have shown a result for a wind the user did not enter. So `ballistic.wind` and `scopeView.wind` are for showing, and `storedWind` goes to the calculators, where `shotWinds` is unchanged.

| Stored wind | Page shows | Result |
|-------------|------------|--------|
| Good | As stored | As before |
| Not an object (`null`, text, array) | Default wind | No wind, as `shotWinds` already gave |
| Speed that is an array, object or boolean | Empty speed box | No result, until the user sets the speed |
| Direction of those shapes, or null, with a speed above 0 | Empty direction box | No result, until the user sets the direction |
| Unknown unit | mph, which is how `shotWinds` reads it | As before |

`setWind` replaces only the changed field, so a damaged field keeps giving no result until the user sets it. The page says nothing about why there is no result, as on #116.

**A timeout keeps `suggestAbove` (#95).** The page shows that hint below the message, and it does not depend on why the search stopped. A search that had finished as the time ran out, with its step at the minimum, is still no solution.

**Y-axis check left out (#112).** The issue says a test could also keep `Y_AXIS_UNITS` in step with the page. The options are inside the page, so that needs a move that this change did not need. The comment still links them.

## Security review

PASS, with one Medium, fixed. The old clock migration read a stored `false` or `null` direction as 12 o'clock, so a damaged direction gave a result and the damage was saved over. It now passes through and gives no result. A missing direction still reads as 12 o'clock, as it always has.

The review rendered hostile names through ApexCharts 5.16.0 in jsdom and found no injection, and ran 23 stored wind shapes with a hard timeout: none hung. The tooltip was traced by reading, not rendered.

## Open points

- Other damaged stored values still crash pages. The review confirmed these by mounting the pages in jsdom, not in a browser. #115 and #118 cover `entries` and `wind` only. All need changed storage:
  - A `zro-profiles` holding `null`, or that is not an array. The first throws at store import on all profile and calculator routes.
  - A wholly null `zro-scope-view`, which throws at store import, and on that page text in place of the store, a null `range` or `atmosphere`, or an object `rotation` or `range.distance`.
  - On the Ballistic page, a null `range`, `atmosphere` or `options`, an object `range.distance`, `step` or `atmosphere.altitude`, or a numeric `visibleColumns`.
  - On the compare page, a bad `range`, or a profile `name`, `ammo` or `zeroDist` that is an object.
- A stored `rotation` of `true` or `[1]` gives a canted result from a value the user did not enter.
- `text-surface-600-300` and `text-surface-900-50` also compile to no CSS (3 uses, noted in the #74 doc). #98 did not cover them.
- A saved profile is not checked when read: see [#89](https://github.com/hawkins48b/cw-zro/issues/89).
