## Summary

The production deploy had stopped working, and there was no CI, so a failing test could not stop a deploy.

**Cause.** `npm ci` failed with `EBADENGINE`. `@capacitor/cli` needs Node 22, the workflow used Node 20, and `.npmrc` sets `engine-strict=true`.

**Correction to #66.** The issue says every listed run had failed. That is wrong: 10 deploys passed on 2026-03-03. Failures began at `a5ac403` ("Add capacitor and electron config"), the commit that brought in Capacitor. That commit is no longer in the repository history and only shows in the Actions run list. So the next deploy updates an existing site, and the owner has confirmed it may replace the content of the FTP root.

**Delivered:**

- Node 22, defined once in `.nvmrc`.
- A CI workflow that tests and builds. The deploy now depends on it, so a failing test blocks production.
- A deploy job that only ships the tested build.
- FTPS with strict certificate checks, replacing plain FTP.
- All actions pinned to a commit SHA.

## How to use

The branch flow is new:

1. Work on a feature branch.
2. Merge it into `develop`. CI runs on pull requests and on pushes to `develop`.
3. Merge `develop` into `main`. A push to `main` runs CI, then deploys to production if CI passes.

`develop` does not deploy anywhere yet; that is [#69](https://github.com/hawkins48b/cw-zro/issues/69).

Deploy Prod can also be started by hand from the Actions tab. Started from `main`, it deploys. Started from any other branch, it runs CI and skips the deploy.

## Technical changes

- [`.nvmrc`](../.nvmrc): Node 22. It is the only place that defines the version.
- [`.github/workflows/ci.yml`](../.github/workflows/ci.yml), new and reusable:
  - Runs `npm ci`, `npm run test:run` and `npm run build`, with npm caching.
  - Uploads `build/` as an artifact, including hidden files, with 1 day retention.
  - Has no push trigger for `main`, because `deploy-prod.yml` calls it there. A trigger would run it twice.
- [`.github/workflows/deploy-prod.yml`](../.github/workflows/deploy-prod.yml):
  - The `ci` job calls `ci.yml`. The `deploy` job needs it.
  - The `deploy` job only downloads the artifact and runs the FTP action. It has no checkout and no npm, so no npm code runs beside the FTP password, and production gets exactly the build that was tested.
  - The `deploy` job has `if: github.ref == 'refs/heads/main'`.
  - The FTP action is v4.4.0 at `110f9186` (node24 runtime), with `protocol: ftps` and `security: strict`.
  - Concurrency group `deploy-prod-${{ github.ref }}`, with `cancel-in-progress: false`. A running deploy is never cancelled, and a newer run replaces a queued one. The ref in the group stops a dispatch from another branch, which deploys nothing, from replacing a queued `main` run.
- Both workflows:
  - All actions pinned to a full commit SHA, on versions that use the node24 runtime.
  - `permissions: contents: read`, and `persist-credentials: false` on checkout.

## Deployment notes

- The first merge to `main` is the first real deploy since 2026-03-03. After it, check that the profile list edit button works on the live site (acceptance criterion of #66).
- `security: strict` needs `FTP_HOST` to match the name on the server certificate. On a mismatch the deploy fails safely, with nothing uploaded. The fix is then to correct `FTP_HOST`.

Owner actions, in GitHub settings and at the FTP host:

1. Rotate `FTP_PWD`. Earlier deploys sent it unencrypted.
2. Move the FTP secrets into the `prod` environment.
3. Restrict the `prod` environment to `main`.
4. Protect `main`.
5. Delete the unused SSH secrets.

## Security review

**PASS on round 2.** Round 1 led to the hardening commit: FTPS with strict checks, the artifact-only deploy job, SHA pins, and the main-only deploy condition.

Remaining risk: the `if` on the deploy job is not a real boundary until owner actions 2 to 4 are done. It lives in the workflow file, so a branch can change it. Only the environment and branch rules can enforce it.
