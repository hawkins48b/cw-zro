# Stopping hangs from an empty wind direction

- **Date:** 2026-11-06
- **Branch:** task/116-wind-direction
- **Issue:** [#116](https://github.com/hawkins48b/cw-zro/issues/116)
- **Status:** Delivered with known issues, not in production yet. It is on `develop` only once merged

## Summary

With a wind speed above 0, an empty or non-numeric wind direction hung `calculateShotPoint` and `calculateFullTrajectory`, so the Ballistic and Scope View pages froze. It needed no changed storage: clearing the direction box was enough. The value was saved first, so a reload froze the page again.

**Delivered:** one function, `shotWinds(wind)` in [`shotWind.js`](../src/lib/utils/shotWind.js). Both calculators call it before the engine, in place of their two copies of the wind code. When it returns null, they give no result.

| Speed | Direction | Result |
|-------|-----------|--------|
| Empty, text, 0, negative, null or missing | Anything | No wind is used, normal result |
| Array, object, boolean | Anything | No result |
| Above 100 m/s, or infinite | Anything | No result |
| Above 0 | Empty or whitespace text | Wind at 0° |
| Above 0 | Text that does not read as a number, or not finite | No result |
| Above 0 | Null, missing, object, boolean or array | No result |
| Above 0 | Over 1e6 degrees either way | No result |
| Above 0 | Finite number or text that reads as one | Wind at that angle |

Text is read as `parseFloat` reads it, so `90abc` stays 90.

No screen, message or stored format changed. A rejected wind shows no result, with no message saying why.

The other callers need nothing. Dope cards build their own wind from fixed values. Trajectory validation and Compare trajectories pass no wind. `calculateMPBR` uses no wind.

### Owner decisions, 2026-11-06

- An empty or whitespace direction counts as 0°, matching the placeholder and the dial. 0° is a tailwind, so clearing the box gives a result for a wind the user did not enter.
- The wind speed limit is 100 m/s, about 224 mph, in any unit. Above it there is no result. 223 mph passes and 224 mph is just over.
- An absolute direction above 1e6 degrees gives no result.
- A stored speed or direction that is an array, object or boolean gives no result, so the page cannot show a wind the result ignores. Empty, text, null, 0 and negative speeds stay no wind.

### Effect on results

The owner approved these changes:

| Input | Before | Now |
|-------|--------|-----|
| Empty direction, speed above 0 | Hang | Result, as 0° |
| Speed from 100 to 500 m/s | A number in 104 of 112 sampled cases | No result |
| Speed above 500 m/s | A number where it did not hang | No result |
| Finite direction over 1e6 degrees either way | A result, as `1e100` gave in the browser control | No result |
| Stored speed `[10]` or direction `[90]` | Flown as 10 mph or 90° | No result. Needs changed storage. Not part of the comparison below |

**Unchanged:** 48384 calls compared between the old and new code, as raw float64 bytes, gave 0 differences. They covered speeds up to 100 in mph and m/s, 150 and 223 mph, directions up to 1e6 either way, 4 loads, 3 atmospheres, cant and speeds that use no wind. No baseline or tolerance was edited.

## Verification

### Tests

- `npm run test:run` gave 1014 passed, 1 todo, in 15 files. `npm run build` passes.
- Rejected winds meet an engine stubbed to throw. Tests on the real engine stop any wind over 100 m/s first, so a raised limit fails a test instead of hanging the run.
- Mutants of the guard fail fast, and none hang.

### Browser

Chromium on the production build, behind a static SPA-fallback server, on the Ballistic and Scope View pages, with a 10 mph wind. A page counted as frozen if it did not answer in 6 seconds. The script is not kept.

| Action | Fixed build | Unfixed `develop` (700764b) |
|--------|-------------|-----------------------------|
| Clear the direction box | Results stay on screen, 21 table rows on Ballistic. Retyping 45 works | Froze |
| Reload, stored direction `''` | Results | Froze |
| Reload, stored direction `abc`, `1e999` or `null` | No result, no freeze | Froze |
| Reload, stored speed `1e999` or `4e5` | No result, no freeze | Froze |
| Reload, stored direction `1e100` | No result, no freeze | No freeze, a result |

The fixed build had no page errors. The control run on `develop` was the first browser confirmation of the bug.

### Hangs under the limits

A grid of 55440 engine runs at or under the limits, on the standard atmosphere, gave 0 hangs. This is a sample, not a proof. "Hang" here means it ran until killed, not that it is proven infinite.

Hangs under the limits remain with a very low BC or an absurd custom atmosphere. See [Remaining gaps](ballistics-model.md#input-guards).

### Not checked

No check of the Capacitor and Electron packages is recorded. Sweeps are samples, not proof for every input.

## Security review

Verdict: see the rounds below.

- Round 1: four Low findings, all resolved.
- Round 2: three Low findings. The comment wording was fixed. One page-side gap, a stored speed that throws, is recorded and not fixed: see [open points](#open-points). The other, a stored `[10]` speed shown on the page but flown as no wind, was fixed by giving no result, on the owner's decision. A third round covered that change.

## Open points

These are in the [Remaining gaps](ballistics-model.md#input-guards):

- **A stored speed such as `{"toString":1}` throws on the page.** It throws in `WindInput.svelte:63` with `Cannot convert object to primitive value`, confirmed by mounting the component. From reading the code, it also throws at `routes/calculators/ballistic/+page.svelte:492`, even with the wind panel collapsed. A stored `wind` of `null` also throws on the page, from reading the code. The calculators are safe from these. All need changed storage.
- **A decimal comma is cut off.** `1,5` reads as 1 for wind speed and direction, confirmed on `shotWinds`. This existed before #116 and is not fixed. A French or German user can reach it by typing.
- A very low BC or an absurd custom atmosphere can still hang under the wind limits. Limits on other inputs are [#92](https://github.com/hawkins48b/cw-zro/issues/92).
- What the direction means is [#106](https://github.com/hawkins48b/cw-zro/issues/106), and saved values are [#89](https://github.com/hawkins48b/cw-zro/issues/89).
