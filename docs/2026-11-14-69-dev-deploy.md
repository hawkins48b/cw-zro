# Dev deployment from develop

- **Date:** 2026-11-14
- **Branch:** task/69-dev-deploy
- **Issue:** [#69](https://github.com/hawkins48b/cw-zro/issues/69)
- **Status:** Delivered with known issues

## Summary

Before this change, only `main` deployed, straight to production. `develop` ran CI and deployed nowhere, so a change could not be checked on a real host before a release. A `dev` GitHub environment existed, but no workflow used it.

**Delivered:** a push to `develop` now runs CI, then deploys the build by FTPS to a separate dev site. The deploy steps are shared with production through one reusable workflow. Production still deploys only from `main`.

The dev site and its secrets do not exist yet. They are owner steps. Until they exist, every push to `develop` shows a warning on the Deploy Dev run, uploads nothing, and ends green. Nothing has run on GitHub yet, and no dev upload has happened.

Nothing changes for users of the app.

## Decisions

### Owner decisions (2026-11-14)

| Topic | Decision |
|-------|----------|
| Branch flow | `develop` deploys to the dev site, `main` to production |
| Transport | FTPS with strict TLS, like production |
| Dev site | A separate site with its own FTP user, limited to its folder |
| Secrets | `DEV_FTP_HOST`, `DEV_FTP_USER`, `DEV_FTP_PWD`, as secrets of the `dev` environment |
| Before the secrets exist | The deploy warns and skips. The run stays green |

The dev secrets have their own names on purpose. A job in an environment also sees the repository secrets, and an environment secret only replaces a repository secret of the same name. A dev job that read `FTP_*` would, without dev values, get the production ones and ship `develop` to production.

## How to use

For developers: merge into `develop` as before. Once the dev site is set up, the Deploy Dev run uploads the build and the dev site shows it.

For the owner, once: set up the dev site and its secrets, following [Deployment: Set up the dev site](deployment.md#set-up-the-dev-site).

1. Create the dev subdomain and its own folder on the host, outside the production web root.
2. Create an FTP user limited to that folder. Its FTP root must be the dev web root.
3. In GitHub, Settings, Environments, `dev`, add `DEV_FTP_HOST`, `DEV_FTP_USER` and `DEV_FTP_PWD` as environment secrets.
4. Re-run the last Deploy Dev run, or push to `develop`, and open the dev site.

Deploy Dev can also be started by hand from the Actions tab. From a branch other than `develop` it runs CI and skips the deploy.

## Technical changes

- [`.github/workflows/deploy-ftp.yml`](../.github/workflows/deploy-ftp.yml) (new). Reusable workflow (`workflow_call`) with one input, `environment` (`prod` or `dev`). One `deploy` job in that GitHub environment, `contents: read`, no checkout and no npm. Same pinned action SHAs as before (`actions/download-artifact` v8.0.2, `SamKirkland/FTP-Deploy-Action` v4.4.0).

  | Step | What it does |
  |------|--------------|
  | Check secrets | Fails unless `prod` runs on `refs/heads/main` and `dev` on `refs/heads/develop`. Checks that host, user and password are set: `FTP_*` for prod, `DEV_FTP_*` for dev, read as `secrets[format('{0}FTP_…', prefix)]`. Missing for dev: a warning and `deploy=false`. Missing for prod: fails. For dev, also fails if `DEV_FTP_USER` equals `FTP_USER` (case ignored) or `DEV_FTP_PWD` equals `FTP_PWD`. The password itself never enters this step, only whether it is set and whether it matches |
  | Download build | The `build` artifact uploaded by `ci.yml`. Only if `deploy=true` |
  | Deploy via FTP | FTPS, `security: strict`, `./build/` to `/`. Only if `deploy=true` |

- [`.github/workflows/deploy-dev.yml`](../.github/workflows/deploy-dev.yml) (new). Runs on a push to `develop` and by hand. Job `ci` calls `ci.yml`; job `deploy` needs `ci`, runs only on `refs/heads/develop`, and calls `deploy-ftp.yml` with `environment: dev` and `secrets: inherit`. Concurrency group `deploy-dev-<ref>`, never cancels a running deploy.
- [`.github/workflows/deploy-prod.yml`](../.github/workflows/deploy-prod.yml): the inline deploy steps are replaced by a call to `deploy-ftp.yml` with `environment: prod` and `secrets: inherit`. Trigger, `ci` job, `main` condition and concurrency are unchanged.
- [`.github/workflows/ci.yml`](../.github/workflows/ci.yml): the `push` trigger on `develop` is removed, because `deploy-dev.yml` calls it there. It still runs on pull requests and through `workflow_call`.
- Guides updated with the change: [`docs/deployment.md`](deployment.md) (state, branch flow, environments, secrets, how a deploy runs, set up the dev site, known gaps), [`docs/testing.md`](testing.md) (CI triggers), [`README.md`](../README.md) (state of `develop`, audit blocks both deploys), [`CLAUDE.md`](../CLAUDE.md) (branches). They were checked against the workflows and match them.

## Deployment notes

- No change to production secrets or settings. `deploy-prod.yml` now delegates to `deploy-ftp.yml`, with the same steps and the same action versions.
- The dev deploy does nothing until the owner creates the dev site, its FTP user and the three `DEV_FTP_*` secrets in the `dev` environment ([steps](deployment.md#set-up-the-dev-site)). `DEV_FTP_HOST` must be the name on the server certificate, or the strict TLS check stops the deploy.
- Optional: limit the `dev` environment's deployment branches to `develop`.

## Security review

**PASS** in 2 rounds. Round 1 had three Low findings:

| Finding | Outcome |
|---------|---------|
| The branch check was only in the calling workflows | Fixed: `deploy-ftp.yml` itself refuses `prod` outside `main` and `dev` outside `develop` |
| The guard compared only the FTP user | Fixed: it also fails when the dev password is the production password |
| `secrets: inherit` lets the dev job read the production FTP secrets | Kept by decision. The guard needs them to compare, and passing secrets explicitly combined with computed environment-secret names is untested. Only the two pinned actions run in that job, with no checkout and no npm |

Pre-existing, not changed: `main` has no branch protection ([#87](https://github.com/hawkins48b/cw-zro/issues/87)).

## Known limitations / follow-ups

- Owner: create the dev site, its FTP user and the three secrets ([Set up the dev site](deployment.md#set-up-the-dev-site)).
- Owner, optional: restrict the `dev` environment to `develop`.
- The dev site serves the same `robots.txt` as production, so search engines may index it. Block indexing on the host if wanted (password protection or an `X-Robots-Tag` header). Nothing in the build tells dev and production apart.
- If [#87](https://github.com/hawkins48b/cw-zro/issues/87) moves `FTP_*` into the `prod` environment, the dev job no longer sees them and the guard against the production account does nothing. One idea: keep the production user name in a `PROD_FTP_USER` repository variable.
- Computed secret names with `secrets: inherit` and a real dev upload are unverified.
