# Max apex independent of the table step

- **Date:** 2026-11-05
- **Branch:** task/85-max-apex
- **Issue:** [#85](https://github.com/hawkins48b/cw-zro/issues/85)
- **Status:** Delivered on `develop`, not in production yet

## Summary

Max apex was taken from the table rows, so it depended on the table step. On the same load (.308 test profile, 200 yd zero):

| Step | Before | After |
|------|--------|-------|
| 1 | 2.2 in at 115 yd | 2.2 in at 115 yd |
| 25 | 2.2 in at 125 yd | 2.2 in at 115 yd |
| 100 | 2.1 in at 100 yd | 2.2 in at 115 yd |
| 250 | 0 in at 27 yd | 2.2 in at 115 yd |

**Delivered:** max apex height and distance are now the same at any table step, and match a step 1 calculation within **1 distance unit and 0.05 in or cm**.

**Why not the library's apex.** `TrajFlag.APEX` is declared in `js-ballistics` 2.2.0-beta.2, but the engine never sets it: 0 rows across 7 profiles.

### Effect on users

The result is shown on the ballistic calculator. Three behaviours change beyond what the issue asked:

- **Rows past the range no longer count.** Only the range the user asked for is considered.
- **Bullet below the line of sight within the range:** max apex is now empty at every step, where it could give 0 in at 27 yd.
- **Bullet still rising at the end of the range:** max apex is the highest point within the range. With a 50 yd range on the load above, that is 1 in at 50 yd.

## Technical changes

All production changes are in `calculateFullTrajectory` in [`src/lib/utils/ballisticCalculator.js`](../src/lib/utils/ballisticCalculator.js). The form, saved data format and translations did not change.

- After the main calculation, the same zeroed shot is fired again on a grid of about one unit that depends only on the range. Max apex is read from those rows.
- This second fire stops at the far zero, or at the range if that comes first or there is no far zero.
- `extraData: true` keeps the zero crossing rows, so a very narrow arc is not lost between grid rows.

### Cost

Every `calculateFullTrajectory` call pays for the second fire, including those from compare trajectories and trajectory validation, which do not show max apex.

| | 100 yd zero | Most, relative to the old full calculation | Worst case |
|---|---|---|---|
| Measured during development, on a desktop | about 0.25 ms | about 1.3 times | about 16 ms more |
| Rerun for this document, in the dev container | 0.33 ms | 1.42 times (1000 yd zero, 1000 yd range) | 10.7 ms more at the longest tried (2500 yd) |

The rerun used the .308 test profile. The old cost was derived by subtracting the second fire, not timed on the old code.

## Deployment notes

Nothing to run or configure.

## Security review

**PASS.**

- **Optional, Low, not changed:** a failure in the second fire would lose the whole result. No input was found that triggers it.
- **Pre-existing, not fixed:** a zero distance of exactly 0 can hang the calculation, and the compare page appears not to block it.

## Known limitations / follow-ups

- **Other key points.** `maxDrop` and `subsonicDist` still read step-dependent rows that can run past the range.
- **Library upgrade.** Check in [#77](https://github.com/hawkins48b/cw-zro/issues/77) whether `js-ballistics` 3.x sets `APEX`.
- **Not tested in a browser.** At coarse steps the apex marker can sit off the drawn line, which is cosmetic.
