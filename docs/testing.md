# Testing

## Running the tests

```bash
npm run test:run                                       # Once, as CI does
npm run test                                           # Watch mode
npx vitest run src/test/ballistics.baseline.test.js    # One file
npx vitest run -t "MPBR search"                        # By name
```

Vitest is configured in [`vite.config.js`](../vite.config.js): `src/**/*.test.js`, jsdom, globals on. The tests need no build. Since [#152](https://github.com/hawkins48b/cw-zro/issues/152) there are two Vitest projects: `unit`, every `*.test.js` as before, and `components`, the `*.svelte.test.js` files, which mount Svelte components in jsdom. Only `components` resolves packages with the `browser` condition, which mounting needs (Svelte's client build); `unit` keeps the resolution it had, so ApexCharts, for one, still loads its non-browser build there. Run one with `npx vitest run --project components`.

## The two ballistics layers

| Layer | Question | Limits |
|-------|----------|--------|
| 1, baseline | Did the result change? | It records what the app computes. It is not proof that the app is right |
| 2, published data | Does the result match an outside table? | Loose bands, two sources. See [Accuracy](ballistics-model.md#accuracy) |

**Baselines are written out by hand**, not stored as snapshots, so a change cannot be accepted by rerunning with `-u`.

Baseline tolerances, also explained at the top of the test file:

| Value | Tolerance |
|-------|-----------|
| Velocity | 0.05 fps, 0.02 m/s |
| Time | 0.0002 s |
| Drop, wind | 0.01 in, 0.03 cm |
| Energy | 0.5 ft-lb, 0.5 J |
| Zero angle | 0.001 MOA, 0.0003 mrad |
| Near and far zero, max drop distance, subsonic distance | 0.2 |
| Apex and max drop elevation | 0.1 |
| Apex distance | 5 units in the old pins. The max apex tests hold it to 1 unit |
| MPBR distances, solver results, display values, dope card labels | Exact |

They are thousands of times above float noise, and small enough to catch a real change: a switch of integrator (Euler to RK4, or a change of step) fails them.

## When a baseline fails

**The owner must approve any change in calculated results. Never overwrite a baseline to make it pass, and never widen a tolerance to make it pass.**

1. Stop and find the cause. A failing baseline is a finding, not a chore.
2. Check layer 2. It decides whether the shift is plausible.
3. Measure the shift: which values, by how much, on which loads.
4. Report it to the owner, on the issue, with the cause. [#77](https://github.com/hawkins48b/cw-zro/issues/77) is the model: 72 baselines were left failing there, with no expected value changed, until the owner accepted the shift and they were re-recorded with an old-to-new list.
5. Change the numbers only after the owner approves. A fix that deliberately changes a value lists the old and new values in its delivery document, as [#86](2026-11-05-86-mpbr-search.md) does.

A known defect is not pinned, so that a test does not make it look correct. The per-shot re-zero is left out for this reason.

## Hangs

`js-ballistics` runs synchronously and can stay in its loop for good on some inputs. **Neither `try/catch` nor a Vitest timeout can stop that**: the timeout needs the event loop, which the loop holds. A hanging test stalls the whole run.

So a test for a hang must not run the hang:

- Stub the solver to throw, then check that the guard stops the call before it. Without the guard, the test fails on the stub. See `vi.spyOn(Calculator.prototype, 'setWeaponZero')` in the baseline tests. Stub the app's `Calculator` from `#lib/utils/ballisticEngine.js`, not the library's: since js-ballistics 3 (#77) the app does not use the library's async `Calculator`. `calculateMPBR` fires before it solves a zero, so stub `fire` too, as `inputLimits.test.js` and `bulletLimits.test.js` do.
- Check the value at each limit too: it must reach the stub. That proves the stub is live and the limit is not stricter than decided.
- If a run stalls, stop it by hand and run the file with `-t` to find the test.

## What the tests do not cover

- **The user interface.** Nothing in the repository runs a browser. Screens, forms and charts are not tested, apart from the current weather button of #152, mounted in jsdom (`currentWeather.svelte.test.js`): jsdom has no layout, no real permission prompt and no network. `apexcharts.test.js` renders charts in jsdom, with no layout, from options written in the test, not from the page code. Browser checks in the delivery documents were run from scripts that are not kept.
- **Electron and Capacitor at runtime.** Only the URL rules, the menu template, the permission handlers and the packaging settings are tested.
- **Rendered PDFs.** Field values and coordinates are checked. No one has reviewed a rendered card.
- **The stores**, mostly. `profileOps.js` is tested in place of the profile list operations. `compareEntries.test.js` and `storedStores.test.js` run the compare, Ballistic, Scope View, profiles, MPBR and Trajectory Validation stores with `localStore` replaced by plain values, so the runes in `localStore.svelte.js` are not run there. `localStore.test.js` covers only a write that storage refuses.

## CI

[`ci.yml`](../.github/workflows/ci.yml) runs on every pull request. [`deploy-dev.yml`](../.github/workflows/deploy-dev.yml) calls it on pushes to `develop`, and [`deploy-prod.yml`](../.github/workflows/deploy-prod.yml) on `main`.

| Job | Steps |
|-----|-------|
| `test` | `npm ci`, `npm run test:run`, `npm run build`, upload `build/` |
| `audit` | `npm run audit:check`, with no `npm ci`, so no dependency code runs |

`build:mobile` is not in CI. Run it yourself when a change can affect it.

Two checks of CI have not been seen on GitHub yet: a run on a pull request, and a failing test blocking a deploy ([#68](https://github.com/hawkins48b/cw-zro/issues/68)). The audit is explained in [Dependency Updates](../README.md#audit).
